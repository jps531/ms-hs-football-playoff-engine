# 2026 Interim UI — Update Spec

Follow-on to `docs/2026_INTERIM_UI_BRIEF.md`. Everything in that brief still
applies — the banned patterns, the tokens, the typography, the accessibility
floor. This document adds three things and does not revise anything already
shipped except the URL shape.

Work in this order. The URL change touches everything else, so it goes first.

1. **URL shape** — move navigation into the path, keep view state in the query.
2. **Bracket view** — a second view, class-scoped, built for the undetermined state.
3. **Share images and meta tags** — per-region OG cards, generated by the daily pipeline.

A backend addition is required for part 2 (section 5). Read that before
scoping the bracket work.

---

## 1. URL shape

### 1.1 The rule

**Path = what you are looking at. Query = how you are looking at it.**

Navigation (class, region, bracket, methodology) belongs in the path, because
those are distinct pages that should be linkable, crawlable, and
redirect-stable. View state (season, week, odds mode, selected team) belongs
in the query, because it modifies a page rather than identifying one.

This is the same split the 2027 app uses, where `?date=` and `?sim=` ride on
top of path routes. Adopting it now means links shared during the 2026 season
keep working after the rebuild.

### 1.2 Routes

| Route | View |
|---|---|
| `/` | Landing — class index (see 1.4) |
| `/standings/{class}` | All regions in a class, condensed |
| `/standings/{class}/{region}` | The region view |
| `/brackets/{class}` | The bracket view (part 2) |
| `/methodology` | Unchanged |

`{class}` is lowercase with the A: `1a`, `2a` … `7a`. `{region}` is the bare
number. So Region 6-3A is `/standings/3a/6` — class first, matching the
long-term route shape, even though the MHSAA writes the region name the other
way round.

### 1.3 Query parameters

| Param | Values | Omitted when |
|---|---|---|
| `season` | year, e.g. `2025` | current season |
| `week` | week number | latest available week |
| `odds` | `projected` \| `tossup` | `projected` |
| `team` | team slug | no team selected |

**Omit defaults from the URL.** A link to the current week of the current
season in Projected mode is just `/standings/3a/6`. This matters more than it
sounds: it is the canonical URL for sharing, for the OG cache, and for search
engines, and a proliferation of equivalent URLs with different query strings
splits all three.

Update the URL with `history.replaceState` for state changes and
`pushState` for navigation, so the back button moves between pages rather than
unwinding every odds-mode toggle.

### 1.4 The landing page

`/` currently drops into a class. Keep that behavior — render the class index
(or the first class's regions) at `/` without redirecting. Do not build a
statewide dashboard; that is the 2027 home feed and half-building it is worse
than not having it.

### 1.5 Redirects

Old query-string URLs are already in the wild. Keep them working permanently:

```
/?season=2026&class=7&region=2   →  301  /standings/7a/2?season=2026
/?class=3                        →  301  /standings/3a
```

Handle this in nginx where possible. Where a 301 is awkward, a client-side
rewrite on load is acceptable as long as it uses `replaceState` so the old URL
does not stay in history.

### 1.6 nginx

Path routes on a static site need a catch-all:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

Note that section 4 changes this — once per-region HTML shells exist, `$uri/`
resolves to a real file for most routes and the fallback only catches the rest.

## 2. Bracket view

### 2.1 What this is for

The question this view answers is **"who might we play, and where?"** No other
Mississippi site answers it. That means the view is built around the
*undetermined* state, not the determined one.

Most bracket UIs are results-first: empty slots waiting to be filled. In
mid-October nothing is seeded, so a results-first bracket renders as an empty
frame and looks broken. Build TBD-first — an open slot showing its possible
occupants with odds is the **normal** state and should look the most
considered. A determined slot is the simple case.

### 2.2 Scope

Build: browse. One class at a time, every round, respecting the season and
week selectors already in the app. Selecting a team highlights its path.

Do **not** build: tap-to-advance or any form of what-if picking, the
tree-to-path morph animation, or a separate "follow a path" view mode. Picking
outcomes is simulate mode, which is a 2027 feature; shipping a partial version
teaches an interaction that will change. **No violet anywhere** — it is
reserved for simulation and must not appear in 2026 for any other purpose.

### 2.3 Structure

Drive the structure from the API. Do not hardcode round counts or bracket
sizes — classes differ and formats change. Render whatever rounds and slots
the bracket endpoint returns, in order.

Where the class splits into halves (North / South), provide a control to
switch between them, defaulting to showing both on wide screens and one at a
time on phones.

### 2.4 Slot states

Three states, visually distinct, never distinguished by color alone:

**Determined** — both teams known, game not yet played. Render as a normal
matchup: two team rows, helmet mark and name, seed, and the host marked. No
percentages; there is nothing to estimate.

**Partially determined** — one side known, the other open. Known side renders
as determined; open side renders as projected.

**Projected** — no occupant locked. Render the possible occupants as rows,
each with its reach odds in a standard odds cell, sorted by probability
descending. Cap the visible list at the top five with a "show all" control;
long tails of sub-1% teams are noise.

**Clinched vs projected must be unmistakable.** A team that has locked its
seed and won its way into the slot is a fact; a team with 94% reach odds is
not. Use the existing clinched badge language and a lock indicator on
determined occupants, and make sure the difference survives a screenshot: a
determined occupant carries no percentage at all, which is itself the signal.

**Played rounds** render as results with scores, the winner emphasized, the
same way completed region games already do. A past season's bracket is
therefore the all-determined case and should work for free — check it.

### 2.5 Slot expansion — the differentiator

Every slot is tappable and expands in place. This is where the view earns its
existence.

**Default expansion** (no team selected) shows:

1. **Possible occupants of each side**, with reach odds. Two short lists,
   labeled by where each side comes from (e.g. "Region 3 champion or Region 4
   runner-up" — whatever the API can say).
2. **Most likely matchups** — the pairings ranked by joint probability, each
   showing the two teams, the probability of that specific matchup, and
   **who would host it**. Show the top six with a "show all" control.

**When a team is selected** (via the existing row-select interaction or the
`team` query param), the expansion flips to that team's perspective, which is
the question fans actually ask:

> **Taylorsville's possible opponents here** — Mize 34% (Taylorsville hosts),
> Bay Springs 28% (away), Richton 21% (Taylorsville hosts) …

One list, one column of opponents, host stated per opponent. This is far
easier to read than a matchup matrix and answers the question directly. Make
this the emphasized path through the feature.

**Hosting must come from the API, not be computed in the browser.** Seeding
comparison rules live in the MHSAA handbook and in the backend already; a
second implementation in JavaScript will drift.

### 2.6 Path highlight

Selecting a team highlights its possible route through the bracket: the slots
it can reach, de-emphasizing the rest. Reuse the existing row-select pattern
and the existing `team` query param, so selection is shared between the
standings and bracket views and survives a link.

De-emphasis means reduced emphasis, not reduced legibility — keep
non-highlighted team names at `--text-secondary` or better. The other teams
are still real information.

### 2.7 Layout

**Wide screens:** rounds as columns, left to right, slots stacked within each
round, connectors between rounds where it helps readability. Expansion opens
in place and pushes the column, not a modal.

**Phones:** one round per screen, horizontal snap scroll, with roughly 12% of
the next round peeking at the edge so the scroll affordance is obvious. A
round scrubber above the bracket (round names, current round marked) gives
direct access and doubles as position indicator. Expansion opens in place.

The snap scroll is the specified long-term pattern — follow it now so the
interaction is already validated when the 2027 bracket is built.

### 2.8 Entry points

- A nav entry to `/brackets/{class}` that keeps the current class.
- From the region view, a link to the class bracket.
- From a team's expanded row in the standings — where per-round reach and
  hosting odds already render — a link into the bracket with that team
  selected.

## 3. What stays the same

For clarity, since the bracket introduces a second view:

- The provenance line continues to double as the controls strip (season, week,
  odds mode). It applies to the bracket view too. This diverges from the
  long-term design, where provenance is passive and controls are separate;
  that divergence is accepted for the interim and should not be "fixed."
- Odds mode applies to bracket odds exactly as it does to standings odds.
- Generic team marks (helmet silhouette in team colors, initials fallback)
  remain correct for 2026. Real helmet artwork lands for 2027.
- The context bar on scroll should appear on the bracket view as well.

## 4. Share images and meta tags

### 4.1 Approach

Generate static assets in the daily pipeline rather than rendering at request
time. The pipeline already runs at 9:30 AM Central with all the data in hand,
and the card is then exactly as fresh as the odds it depicts — which is also
the honest thing to do.

For each region (roughly 56 of them), the pipeline writes:

1. **An OG image** — `/static/og/{class}-{region}.png`, 1200×630.
2. **An HTML shell** — `/standings/{class}/{region}/index.html`, containing
   the correct `<title>`, `<meta name="description">`, `og:title`,
   `og:description`, `og:image`, and `twitter:card` tags, plus the same app
   bootstrap as the current `index.html`. The JS app takes over on load and
   renders as it does today.

Also generate a per-class shell and image, and keep the existing generic one
as the fallback for any route without a specific shell.

This gets correct link previews **and** indexable pages for every region,
which matters a great deal for a site people will find by searching their
school's name. It needs no runtime image service and no build step, which
keeps the interim architecture intact.

### 4.2 Card content

Dark by default — the long-term share cards are dark and read as broadcast
graphics. Keep it simple and legible at thumbnail size:

- Region name in Nippo Bold, large.
- The headline sentence, in Inter SemiBold, wrapped to at most three lines.
- The top three or four teams: position, name, record, playoff odds in the
  odds ramp.
- The provenance stamp — "Through Week 8 · Oct 24 · Projected" — in the small
  tracked style. **Baked in, always.** A card that does not say what data it
  reflects is a card that can lie three days later.
- `mshsfootball.com` as a footer.

No gradients, no decorative shapes, no icons that are not already in the
system. The typography and the odds ramp are the design.

Pillow can do all of this; it needs the Nippo and Inter TTF/OTF files
available to the pipeline.

### 4.3 Meta copy

Title: `Region 6-3A playoff race — Mississippi High School Football`
Description: the headline sentence, truncated to ~155 characters.

Do not template the description into something generic. The headline sentence
is the most interesting thing the product can say and it is different for
every region — that is what makes a shared link worth clicking.

### 4.4 Scope control

Regions and classes only. Team-level and bracket-level cards can follow once
this pattern proves out; do not build them in this pass.

## 5. Backend: matchup probabilities

**Verify this against the repo before scoping the bracket work — it may be the
larger half of the job.**

The slot expansion in 2.5 needs the probability of each *specific matchup*,
plus who hosts it. The existing endpoints return per-team marginals
(`p_reach`, `p_host_given_reach`, `p_host_overall`), which is not the same
thing.

**Do not compute matchup probability by multiplying marginals.** `P(A) × P(B)`
is only correct when the two sides are independent. In the first round, where
each side is fed by a different region, that is roughly true. In later rounds
both sides can draw from overlapping sets of teams and the assumption breaks —
in the worst case producing a non-zero probability that a team plays itself.
The resulting numbers would be wrong in exactly the situations fans care most
about.

The correct source is the Monte Carlo that already produces the reach odds.
Each simulated bracket realizes a concrete occupant for both sides of every
slot. Counting those pairs costs almost nothing on top of the existing run:

For each slot, accumulate a map of `(team_a, team_b) → count`, and alongside
it the host in that realization. At the end, `p_matchup = count / trials` and
`p_host_a = host_a_count / count` (hosting conditional on the matchup
occurring, which is the number the UI needs).

Expose per slot:

```
slot_id, round, half
occupants_side_a: [{ team, p_reach, is_locked }]
occupants_side_b: [{ team, p_reach, is_locked }]
matchups: [{ team_a, team_b, p_matchup, p_host_a }]
```

Truncate `matchups` server-side at a sensible floor (say, drop pairs below
0.5%) with the remainder aggregated, so the payload stays small and the client
never has to decide what to hide.

Two invariants worth asserting in tests, both of which catch real bugs:

- Within a slot, each side's `p_reach` values sum to 1.0.
- `matchups` probabilities sum to 1.0, and no matchup pairs a team with
  itself.

If the Monte Carlo output is not currently retained in a form that allows
this, that retention is the actual work item — and it is worth doing properly
rather than approximating, because approximate matchup odds are the kind of
error a knowledgeable fan will spot and post about.

## 6. Out of scope

Unchanged from the original brief, and worth restating because the bracket
makes some of these feel close:

Simulate mode in any form, including tap-to-advance on bracket slots. Violet.
Team pages, game pages, scoreboard, rankings, helmet browser, championships.
Accounts, following, favorites. Submissions. Admin. Maps. The home feed. The
timeline scrubber (the week dropdown stays). Real helmet artwork.

## 7. Definition of done

1. `/standings/3a/6` loads the region view directly, and an old
   `?class=3&region=6` link redirects to it.
2. A current-week, Projected-mode link carries no query string at all.
3. The bracket renders usefully in mid-October, when nothing is seeded —
   open the deployed site and check that it looks designed, not empty.
4. A determined occupant and a 94% projected occupant cannot be confused,
   including in a screenshot with no surrounding context.
5. Tapping a slot answers "who might we play and where" in one screen, and
   with a team selected it answers it in one short list.
6. On a phone, the bracket snaps round by round and the next round peeks.
7. Pasting a region link into Facebook or iMessage shows the region's own
   card with its own headline sentence and a provenance stamp.
8. Matchup probabilities come from simulation counts, not multiplied
   marginals, and the self-matchup test passes.
9. Past seasons' brackets render as completed results.
10. No violet anywhere.
